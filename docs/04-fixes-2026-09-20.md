# Repair log, 2026-09-20

Eight defect reports, what was actually wrong, and what changed. Each has at
least one regression test named after the behaviour, so that if a fix is ever
undone the suite says which one and why it mattered.

---

## 1. The pipeline reported success for work it did not do

**Confirmed.** The worker started with `MonitoringLoop(handlers={})`. Every
unwired stage was recorded as `ok=True, degraded=True`, and the summary said 20
stages ok. A dead pipeline that reports success is worse than one that crashes,
because nobody investigates it.

**Changed.** Stage status is four-valued: `ok`, `skipped`, `unwired`, `failed`.
Counts are separate and the summary prints all four. An empty handler map now
prints `0 ok, 0 skipped, 20 unwired, 0 failed` and a cycle status of
`degraded`. A stage that wrote some rows and then failed sets `partial`, which
the summary names.

Real handlers were then written: `services/worker/app/pipeline.py` wires
import, raw persistence, FX, policy normalisation, fair value, liquidity,
arbitrage, scoring, prior-snapshot comparison, alerting and snapshot
persistence. Stages that depend on a disabled source report `skipped` with the
reason; the nine stages with no data route at all report `unwired`.

**Manual import route.** `pokearb_core/ingest/manual.py` takes a documented CSV
or JSON schema, requires a named importer and an evidence URL, and identifies a
batch by the hash of its content, so re-importing the same file inserts
nothing. `schema_help()` prints the column contract. Synthetic demonstration
rows are labelled `synthetic_demo` at the source and the row, and a database
trigger refuses to attach a synthetic row to a production source.

**Idempotency.** `cycle` and `cycle_stage` persist status; a re-run of the same
`cycle_id` skips stages that already completed. Sales are unique on
`(source_id, external_id)`. Alerts are unique on
`(opportunity_id, fingerprint)`, enforced by the database rather than by an
application check that two workers could race.

## 2. The database layer lost identity and grading

**Confirmed, twice over.**

`Repository.sales_for()` never selected `graded_item_id`, so a PSA 10 sale was
returned as `Sale(is_graded=False)` and priced the raw card. The same query
coerced `condition_confidence` with `or "1.0"`; zero is falsy in Python, so a
sale whose condition nobody could assess was loaded as fully confident.

**Changed.** The query joins `graded_item`, returns `is_graded`, `grader` and
`grade`, and takes a `graded` filter that defaults to raw. Confidence is read
with an explicit `is not None` check. Scoping parameters for market, language
and known-at were added, and `Sale.grade_bucket` gives raw and each
grader/grade pair its own valuation bucket.

`compute_fair_value` now enforces scope itself rather than trusting the caller:
out-of-bucket, out-of-market and wrong-language sales are recorded in
`excluded` with the reason. Graded valuation is not silently treated as raw; a
bucket with insufficient evidence returns `sufficient=False`.

## 3. Condition was computed and then ignored

**Confirmed.** Quick Check built a condition distribution and passed the
near-mint fair value straight into the arbitrage maths. The confidence haircut
in the scorer shrank the score but not the price the model thought it could
sell for.

**Changed.** `condition_value_curve()` prices every point on the ladder from
its own completed sales where they exist and derives the rest from the NM
anchor by the documented multiplier, labelling each point `OBSERVED` or
`MODELLED`. `expected_value()` weights those by the condition probabilities.
The result drives expected proceeds, profit, ROI, the purchase limits and the
simulations, and is returned as `condition_adjusted_fair_value` with the ladder
in `condition_value_ladder`.

If a condition carrying meaningful probability has no value, the answer is
`INSUFFICIENT_DATA` with the reason, not a substituted near-mint value.

## 4. The solver disagreed with the forward calculation

**Confirmed and reproduced exactly.** With a 10 percent proxy fee, a 5 percent
duty rate and a 40 percent required return:

| Gross resale | Returned maximum | Actual ROI |
|---|---|---|
| EUR 100 | 5,785 JPY | 21.01 % |
| EUR 220 | 15,336 JPY | 35.17 % |
| EUR 400 | 29,665 JPY | 37.77 % |

**Cause.** The affine slope was derived by hand beside the forward formula and
treated the proxy fee as dutiable and VATable, which the forward formula did
not. The intercept was then taken as a residual at a probe point, so both
coefficients were wrong. A solver that restates the cost model in a second
place will eventually restate it wrongly.

**Changed.** The solver no longer restates anything. Price bands are cut at
every real discontinuity (the EUR 150 duty threshold, the traveller allowance
where it applies, the JPY 5,000 tax-free minimum), and within a band the
largest feasible whole yen is found by binary search directly against
`compute_economics`. Monotonicity is only assumed inside a band, which is what
the band boundaries exist to guarantee. Every answer is verified forward, and
the next yen is verified to fail.

| Gross resale | New maximum | ROI at it | ROI one yen higher |
|---|---|---|---|
| EUR 100 | 2,137 JPY | 40.02 % | 39.997 % |
| EUR 220 | 12,353 JPY | 40.01 % | 39.996 % |
| EUR 400 | 26,815 JPY | 40.00 % | 39.998 % |

When no price in the model clears the requirement, the answer is `None`. That
is a real answer, not an error.

## 5. Incomplete landed costs produced recommendations

**Confirmed.** A hand-carried purchase above the traveller allowance returned
numeric costs with duty and VAT at zero, under a note saying they were not
modelled. The note does not reach the arithmetic.

**Verified against the source, not assumed.** From
https://info.skat.dk/data.aspx?oid=2230232 (Den juridiske vejledning, F.A.29
Rejsegods): relief covers goods for private use; the import must not be of
commercial character; goods cannot be treated as for own use when imported with
a view to resale; above the value limit, duty and tax fall on the goods in
their entirety and the value of an item cannot be split; two travellers may not
pool or divide the limit. From
https://www.japan-guide.com/news/tax-free-shopping.html: from 1 November 2026
the traveller pays the tax-inclusive price and claims a refund at departure
after a customs procedure, purchases are limited to what can be personally
carried out, and if any item on a receipt is absent the whole receipt becomes
ineligible.

**Changed.**

* `CostAssumptions.acquisition_purpose` defaults to `RESALE`. Resale inventory
  gets neither the traveller allowance nor the Japanese departure refund, and
  the notes say why with the source URL.
* A personal import above the allowance raises `PolicyUnverifiedError` when the
  tariff rate is unverified, instead of costing duty and VAT at zero.
* Thresholds are assessed on `basket_value_jpy`, the receipt or consignment,
  not on the single card.
* `LandedCost` separates `upfront_cash_eur` from `total_eur`, with
  `expected_refund_eur` between them. The two reconcile exactly.
* `LandedCost.unresolved` blocks purchase limits: an understated cost must not
  produce a limit that is too generous.

## 6. Two different financial models wore the same names

**Confirmed.** The arbitrage engine used the full cost stack; the scorer
independently assumed net proceeds were 90 percent of gross resale. The two
ROIs were different numbers with the same label, and the simulations varied a
scaled ROI rather than recalculating.

**Changed.** `compute_economics()` is the single calculation.
`resale_economics_fn()` freezes the buy side and is handed to the scorer, which
calls it for the point estimate and for every simulated draw, so the tail
reflects the real fixed-cost structure rather than a proportional assumption.
`Economics` states its denominator: profit is economic, the denominator is cash
deployed, and `capital_basis` says so in words. The verdict now respects both
the required return and the purchase limit through the new suppression reasons
`ABOVE_MAX_BUY`, `BELOW_REQUIRED_RETURN` and `LANDED_COST_UNRESOLVED`.

Material cost inputs are request fields with validation. An unrecognised
scenario is refused rather than defaulted to hand carry, and an unstated
shipping or proxy cost is refused unless the operator explicitly asserts that
the zero is real.

## 7. Historical evidence was not reproducible

**Confirmed.** Passing the same sale three times satisfied the evidence
minimum, and look-ahead was prevented only by filtering on the transaction
date.

**Changed.** `Sale` carries `known_at` and `external_id`. Fair value
deduplicates on stable transaction identity and then on a content fingerprint
(same source, same day, same price), records every duplicate in `excluded` with
the reason, and excludes evidence whose `known_at` is after the calculation
time. Listing prices come from `listing_observation`, so a historical read sees
the price that was in force then, and successive observations of one listing
remain one listing.

Snapshots persist the model version, risk configuration, cost assumptions, FX
rates used, policy sources, the sale ids behind the value, and the `as_of`
instant.

An incomplete import is not treated as evidence that a listing was removed:
`end_listings_absent_from` does nothing unless the caller asserts the feed was
complete.

## 8. Implementation claims outran the implementation

**Confirmed.** `EbaySoldAdapter.fetch_sales` raised `NotImplementedError` while
its message claimed the parser and schema were implemented and unit-tested
against recorded fixtures. Neither existed. `PsaCertAdapter.fetch_cert` claimed
schema and tests were in place.

**Changed.** Both claims are gone. Every gated adapter's `capabilities()` now
reports `parser_implemented` and `verified_live_access` separately from what
the remote API offers, and `tests/test_claims.py` asserts that no gated source
claims verified live access. PriceCharting is the one gated adapter whose
parser genuinely exists, so its test exercises it rather than asserting its
absence.

Three categories are now distinguished in the code and the docs:

* **documented-schema** tests, written from published documentation, which
  prove only that our reading matches the document;
* **recorded-response** tests, written from a payload actually observed;
* **verified live access**, which no gated source has.

## Addendum, 2026-09-21: found by an independent run

The project was rebuilt from the archive in a clean Claude Code cloud VM. All
95 tests passed and the demo reproduced every figure exactly, including the
EUR 33.15 landed cost, the 0.6086 ranking ROI and the 14,654 yen maximum. Three
problems surfaced anyway.

**Alerts fired on non-material changes.** The demo heading promised one alert
per material state and the table held two. `stage_compare` built the prior
state from unrelated columns: the prior maximum buy price stood in for the
prior asking price, and the prior sale count was hardcoded to zero. Every
comparison therefore read as a large price drop plus new sales, so any change
at all realerted, and only the exact-fingerprint constraint stopped identical
states from repeating. The state each cycle compares against is now stored with
the snapshot and read back field for field. Two new integration tests
reproduced the defect before the fix: a 0.8 percent price move no longer
alerts, and a 7.7 percent drop alerts with only the reasons that are true. The
demo now prints each alert with its reason, scoped to its own card.

**The Python pin was stricter than the code.** `requires-python` said 3.12;
the VM's interpreter is 3.11.15. The full suite passes under 3.11.15, so the
pin is now `>=3.11`.

**Nothing survived the session.** A SessionStart hook now rebuilds the
environment in each cloud session, and the Makefile defaults `DATABASE_URL` to
the database it creates.

Also fixed: the pytest-asyncio loop-scope deprecation warning, via
`pytest.ini`; integration tests now clean up after themselves, so a demo run
after the suite no longer sees the suite's rows; the Makefile calls `python3`,
since Ubuntu ships no bare `python`. Model version is now `2026.09.21-1`.
